Multi-Tenant API Gateway

Design brief: the architecture (every component) and the end-to-end workflow

What it isA reverse proxy in front of many backend services, shared by many tenants. Every request is authenticated, checked against the tenant's policy, routed at runtime, proxied with resilience controls and audited exactly once.
StackJava 21 · Spring Boot 3.5 (Spring MVC on virtual threads) · Apache HttpClient 5 (pooled) · Caffeine · JDBC + H2 (portable SQL) · Nimbus JOSE (RS256 JWT). No Redis, no message broker.
Codebranch feature/GW-3-in-memory-demo, step 32 (bf9269c); 45 main classes; 152 unit + 62 integration tests, line coverage gate 80%
How to read thisPart 1 is the map: what each component does and why. Part 2 follows one request (and one admin change) from start to finish. Every row names the class and the test to open for a deep dive.

Design principles (they explain most decisions below)

PrincipleWhat it means in the code
Reject = throwEvery stage passes or throws GatewayException(code). Rendering to RFC 9457 problem+json happens in one place. A rejected request cannot reach an upstream: the structure guarantees it, not a convention.
Exactly one audit entry per requestThe outermost filter creates the record and writes it in finally; later stages only fill in fields.
Canonicalise the path onceRouting, allowlist and forwarding all use the same canonical path; ambiguous paths (.., encoded slashes) are a 400.
No I/O per request on the hot pathRoutes, RBAC data and rate-limit buckets are in memory. Tenants and token revocations are read from the database at most once per 5s per instance, through a single flight and a circuit breaker.
Cheap checks first, shared resources lastQuota is spent only after path, scope and permission pass; the route's shared bucket after the tenant's own quota.
Static stabilityIf the config database is down, the gateway keeps serving from its last snapshot and cached tenants; it never replaces good config with an empty one.

PolicyEnginePath allowlist → scope → RBAC → per-user quota → tenant quota → route limit.Ordered so rejected requests spend no quota, and the shared route bucket is spent last.PolicyEngineTest

RendezvousHashSticky routes: the same tenant always gets the same upstream, by weight.Raising the canary's weight only moves tenants onto it.RendezvousHashTest
Resilience
CircuitBreakerClosed → open → half-open, count-based window; one per upstream host:port, plus rate-limiter and config-db.Generation numbers drop stale results; 4xx and pool saturation are not failures; open upstream → fallback to the heaviest healthy one.CircuitBreakerTest
RetryBudget, BackoffRetries only for bodiless GET/HEAD/OPTIONS on connect failure or timeout; full-jitter backoff; retries + hedges ≤ ~10% of requests.Integer token arithmetic; budget stops retry storms when everything fails.RetryBudgetTest, HedgingBudgetIT

1.4 State: what lives where

StateWhereLifetime and consistency
Routes, custom roles, role assignmentsSnapshot in memoryReloaded whole when the version token changes: at once on the writing instance, ≤ 5s on others.
Tenants, token revocationsCache in memory (5s TTL)Loaded on first use through a single flight; stale if the database fails.
Rate-limit buckets, bulkhead permits, breaker states, retry budgetMemory, per instanceLost on restart without harm. Per instance: N instances ≈ N× quota (a shared store is the documented next step).
Tenants, routes, roles, assignments, revoked tokens, versionConfig databaseSource of truth. Tables: tenants, routes (unique prefix), roles, role_assignments, revoked_tokens, config_version.
Operators, built-in roles, signing keyapplication.yml / environmentReviewed as code; the same on every instance.

#Stage (class)CheckOn failureWhy here

11Tenant quotatenant:id bucket (rate + burst)429 RATE_LIMITEDThe tenant's contract
12Route limitroute:id bucket, all tenants together429 ROUTE_RATE_LIMITEDShared, so spent last
13Bulkhead (ConcurrencyLimiter)Tenant's requests in flight < limit429 CONCURRENCY_LIMITEDProtects the pool from slow tenants
14Breaker (CircuitBreaker)Picked upstream admits, else heaviest healthy one503 CIRCUIT_OPEN (all open)Fail fast instead of waiting on a dead upstream

All 429 and 503 responses carry Retry-After. Every policy rejection (400, 401, 403, 404, 413, 429, 503 CIRCUIT_OPEN) is audited as DENY with its reason, and tests assert the upstream received nothing; dependency failures (CONFIG_UNAVAILABLE, 502/503/504 from the upstream call) are audited with their code but not as a denial.

2.5 When something fails

FailureWhat the gateway does
Config database downRoutes and RBAC from the last snapshot; cached tenants served stale; unknown tenants 503 at once once the config-db breaker opens; revocation checks fail open (counted, alerted); admin writes fail.
Config database lost its dataMissing version detected: old snapshot kept, tenant reloads refused so cached values stay.
Upstream down or erroringIts breaker opens; traffic falls back to the route's healthiest upstream; 503 with Retry-After if all are open.
Upstream slowResponse timeout → 504; hedging (if enabled) answers from the other upstream; bulkhead caps how much of the pool one tenant holds.
Connection pool exhaustedWait ≤ 500ms for a connection, then 503 UPSTREAM_SATURATED; not counted against the upstream.
Rate limiter failingIts breaker opens; fail open by default (serve without limits) or 503 if configured.
Audit writer behindQueue (10,000) fills, entries dropped and counted; requests never wait.
Traffic burst / thundering herdPer-IP, per-user, per-tenant, per-route buckets; single flight on cache misses; jittered backoff and config polling.
Built for, not built (good places to dive deep): Kafka behind the AuditSink interface; OpenTelemetry export using today's trace and span ids; a Redis token bucket behind the RateLimiter interface (fixes N× quota with N instances); push invalidation of config (Postgres LISTEN/NOTIFY); bot detection before authentication; nearest-region routing in front of the gateway.
