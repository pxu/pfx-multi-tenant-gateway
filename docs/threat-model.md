# Threat model

## Assets and trust boundaries

| Asset | Why it matters |
|---|---|
| Upstream services and their data | What the gateway protects. Upstreams trust `X-Tenant-Id`, `X-User-Id` and `X-Role` from the gateway. |
| Tenant isolation | One tenant must never act as, or degrade, another. |
| Signing key | Whoever holds it can mint a token for any tenant. |
| Admin user keys and sessions | A user can do what their roles allow; with the `admin` role, rewrite routes and tenant policy and mint tenant tokens. |
| Audit trail | Needed to investigate abuse after the fact. |

Trust boundaries: **internet → gateway** (untrusted clients), **gateway → upstreams** (internal
network; upstreams trust the gateway), **operators → admin API** (separate credentials: per-user keys, sessions with one role, RBAC per endpoint),
**gateway → config database** (embedded in the demo; a shared database on a private network otherwise).

## The authenticated-but-malicious tenant

The attacker holds a valid token for tenant `evil` and controls every byte of their requests.

### What they can do

| Capability | Bounded by |
|---|---|
| Call the routes their tenant may call, for the services in their token's scope, with the actions their role allows | That is the intended access. |
| Send traffic up to their quota | Per-tenant token bucket (per-minute rate plus a burst cap, so the minute cannot be spent in one second), enforced in the gateway's memory. **Gap:** each instance counts on its own, so with N instances a tenant gets up to N× its quota (the demo runs one instance; a shared store fixes it). Over-limit requests never reach upstreams. |
| Get many requests rejected cheaply (bad paths, missing scopes) | Rejections do no upstream work, and a per-address limit runs before authentication, so a flood of junk tokens from one address stops costing signature checks after its burst. **Gap:** many addresses (a botnet) each stay under it. |
| Pick trace ids or force sampling through `traceparent` | Only a valid header is joined; the gateway's own span and call spans are always generated by it; the client's `traceparent` is never forwarded as is. **Gap:** with `continue-client-traces: true` (default) a caller chooses its trace id and the sampled flag; set it to `false` to start every trace at the gateway. |
| Make an upstream they may call return 5xx and trip its circuit breaker | **Gap:** breakers are per upstream, not per tenant, so the upstream fails fast for other tenants too, for `open-duration` (10s). Per-tenant breakers would instead keep hammering a genuinely broken upstream. |
| Send large or slow requests | Bodies are streamed, never buffered whole, and capped at `max-request-body` (Content-Length up front, chunked while streaming). The upstream response timeout bounds slow upstreams; the connection pool caps connections per upstream (503 when full). A per-tenant bulkhead caps its requests in flight (default 50; `maxConcurrentRequests`): beyond it, 429 at once, so a slow tenant cannot occupy most of an upstream's pooled connections. |
| Keep using a leaked token of their own until it expires | Max TTL 1h (default 15 min). Revoke that one token by its `jti` (`POST /admin/tokens/{tokenId}/revoke`): immediate on the instance that handled the admin call, ≤ 5s elsewhere. Kill switch: disable the tenant. **Gap:** revocation fails open: while the config database is down, an instance that has never checked the revoked token serves it (counted, alerted); and a database that loses its data forgets its revocations. |

### What they cannot do

| Attack | Why it fails |
|---|---|
| **Act as another tenant:** edit `tid` in the token, or send `X-Tenant-Id: victim` | The tenant comes only from the signature-verified `tid` claim. Any client `X-Tenant-Id`, `X-Request-Id` or `X-Forwarded-*` header is dropped, and the gateway sets its own. |
| **Forge a token:** `alg: none`, HS256 "signed" with our public key (algorithm confusion), a token signed with another key | The key selector accepts RS256 with our key only. Unit tests cover each case. |
| **Escalate scopes** | Issuance refuses scopes outside the tenant's `grantableScopes`. At request time the effective scopes are `token ∩ grantable`, so removing a scope from a tenant also applies to tokens already issued. |
| **Act as another user or role:** edit `sub`/`role` in the token, send `X-User-Id` / `X-Role` | User and role come only from the signed token, and the user must hold the role in their tenant. Client identity headers are dropped; the gateway sets its own. |
| **Do an action the role does not allow** (e.g. delete with a write-only role): `POST` + `X-HTTP-Method-Override: DELETE`, or a lower-case `delete` | The action comes from the request method, compared case-insensitively, and the override headers (`X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override`) are not forwarded. **Gap:** a `_method` form or query parameter is still passed through; upstreams must not honour it. |
| **Escape the path allowlist** with `/allowed/../admin`, `%2e%2e`, `%2f`, `//`, `;param`, double encoding | The path is canonicalised once, before any decision, and anything ambiguous is rejected with 400. Routing and the allowlist compare against that one canonical path, using segment-aware prefixes (`/orders` does not allow `/ordersX`). |
| **Reach the admin API** | `/admin/**` (except login) requires an admin session token. Tenant tokens are signed with the same key but have a different audience (`gateway-tenants`, against `gateway-session` for sessions) and must carry a `tid`, so they are not accepted there whatever their scopes, and sessions are not accepted on the data plane. Tests cover both directions. |
| **Choose where requests go (SSRF)** | Tenants cannot create or change routes. The request path is appended to the configured upstream URL, so it cannot change the host. Operator-configured upstreams are validated: http/https only, no credentials, no link-local addresses (e.g. 169.254.169.254 metadata), no loopback in production. |
| **Use up another tenant's quota** | Counters are keyed by the tenant id from the token. |
| **Hide behind a forged address** (`X-Forwarded-For: 10.0.0.1`) to dodge the per-address limit or poison the audit log | The address is the TCP peer; `X-Forwarded-For` is only read when the peer is a configured trusted proxy, and then only the hops our proxies appended count. Hostnames in the header are never resolved. |
| **Learn internal topology** | Error responses never contain upstream hostnames or exception text; that goes to the audit log only. 401 messages are deliberately coarse, so a forged token does not learn which check it failed. |
| **Hide from, or forge entries in, the audit log** | Every request that reaches the application is audited in a `finally` block, including rejections before authentication. Entries are JSON-encoded, so newlines or quotes in a path cannot inject fake lines. The request id is generated by the gateway. |
| **Harvest credentials through an upstream** | The client's `Authorization` header is never forwarded. |

## Other actors (STRIDE)

| Threat | Example | Mitigation / status |
|---|---|---|
| Spoofing | Unauthenticated internet client | JWT required on every data-plane path; 401 + `WWW-Authenticate`. |
| Tampering | Token modified in flight | Signature check; TLS expected at the edge. |
| Repudiation | Tenant denies making a request | Audit entry per request (tenant, path, route, upstream, decision, status, latency) with a request id that is also returned to the client and sent upstream. |
| Information disclosure | Error bodies, forwarded headers | Coarse errors; `Authorization` not forwarded; hop-by-hop headers stripped in both directions. |
| Denial of service | Request floods, slow upstreams | Token buckets per address (before authentication), per user and per tenant; body-size cap; pool limits with a lease timeout; circuit breakers; bounded audit queue. Per-tenant bulkhead (requests in flight). |
| Elevation of privilege | Tenant → admin, tenant → more scopes | Separate admin credentials; scopes capped by the tenant's grantable set at issuance and at request time. |
| Elevation of privilege | Tenant user → more actions (a reader deleting) | The token names one role; RBAC checks `service:action` (from the HTTP method) against that role on every request, before quota and before the upstream. The user must still hold the role, so revoking it ends access at once. A user's other roles never add up. Client `X-User-Id` / `X-Role` headers are dropped. |
| Elevation of privilege | Operator → more than their role | Users get permissions only through the one role chosen at login, never the union of their roles. Every admin endpoint declares a permission (a build-time test fails otherwise), and an undeclared one is refused. The role assignment is rechecked on every request, so removing it ends existing sessions. |
| Elevation of privilege | Operator with `rbac:write` grants themselves more | Management permissions exist only in built-in roles, which cannot be changed through the API; custom roles may hold service permissions only (400 otherwise); operators' own assignments are in config and limited to built-in roles. So `rbac:write` grants access to services, never to the management API. Tenant users cannot hold roles with management permissions. **When** operator assignments become editable, add the Kubernetes "escalate" rule. |
| Repudiation | Operator denies a config change | Audit entries have `actor` and `role` for every admin call, including failed logins. |

## Compromise and failure scenarios

* **Signing key leaked:** anyone can mint tokens for any tenant. Rotate the key (new `kid`), which
  invalidates all tokens. Mitigation: keep it in a secret manager or KMS, and move issuance into its own
  service so gateway instances hold only the public key.
* **Admin user key leaked:** the holder can log in as any of that user's roles. Replace the key hash
  (only that user is affected), and remove the user's roles to end their current sessions at once.
  Mitigation: least-privilege role assignments, admin API on an internal network only, SSO/OIDC.
* **Config database unavailable:** routing keeps working from the last snapshot, and tenants already
  cached keep working from their last value (stale if error); a tenant this instance has not seen yet
  gets 503. Once the `config-db` breaker opens (after a few failed reads, each bounded by a 2s
  connection timeout), those requests fail at once instead of waiting. Admin writes fail.
  Rate limiting does not depend on it (buckets are in memory), so quotas stay enforced.
* **Config database loses its data:** the missing version is detected and the last snapshot is kept,
  so traffic keeps flowing while config is restored from a backup.
